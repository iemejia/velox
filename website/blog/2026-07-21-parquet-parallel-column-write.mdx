## TL;DR

We evaluated Arrow's existing parallel Parquet column-write path for use in
Velox. Our first end-to-end benchmark reported only 1.53-1.57x at eight workers
and appeared consistent with a ~1.7x ceiling. That interpretation was wrong.

The machine exposed eight vCPUs but only four guest-visible cores with SMT
topology. More importantly, the timed region included an unstable
Velox-to-Arrow export phase and compared two different execution paths without a
threaded one-worker control.

We rebuilt the study around the vendored Arrow writer itself: export once before
timing, disable dictionary encoding where required, restrict each treatment to
one SMT sibling per guest-visible core, randomize 30 paired process samples, and
report bootstrap confidence intervals.

For 20 columns and 100K rows, warm row-group latency scaled as follows:

| Workload | 2 workers | 4 workers |
| --- | ---: | ---: |
| Flat 128-byte VARCHAR, dictionary off, ZSTD | 1.81x [1.77, 1.85] | 2.92x [2.84, 2.95] |
| Low-cardinality flat VARCHAR, Parquet dictionary enabled, ZSTD | 1.67x [1.62, 1.70] | 2.58x [2.52, 2.63] |
| BIGINT, dictionary off, uncompressed | 0.94x [0.93, 0.95] | 0.95x [0.93, 0.96] |

The real conclusion is workload-dependent: parallel top-level field writing can
scale well for CPU-heavy writes, but its fixed overhead hurts lightweight
fixed-width writes. The experiment does **not** establish a hard ceiling beyond
four guest-visible cores.

## Where concurrency exists

Velox writes Parquet through a vendored copy of Arrow's Parquet writer. For
each input batch, Velox exports a `RowVector` to an Arrow `RecordBatch` and
calls `FileWriter::writeRecordBatch`.

Arrow first constructs one `ArrowColumnWriterV2` for each top-level Arrow
field. With threading enabled, it submits each writer's complete `write()`
operation through `::arrow::internal::ParallelFor`:

```cpp
if (arrowProperties_->useThreads()) {
  RETURN_NOT_OK(::arrow::internal::ParallelFor(
      static_cast<int>(writers.size()),
      [&](int i) {
        return writers[i]->write(&parallelColumnWriteContexts_[i]);
      },
      arrowProperties_->executor()));
}
```

Each task includes definition- and repetition-level generation, physical
conversion where needed, statistics, page formation, encoding, compression,
and buffered serialization. A nested top-level field is still one task; its
Parquet leaf columns execute sequentially inside that task.

Some work remains sequential. Field-writer construction happens before task
submission, and buffered column writers close in order during row-group
finalization. Source inspection identifies these boundaries, but only
measurement can tell us whether they matter for a particular workload.

## The proposed Velox design

The initial prototype enabled Arrow threading without providing an executor,
which uses Arrow's process-wide CPU pool. Besides giving Velox no control over
parallelism, this exposes the documented same-executor starvation/deadlock
scenario: outer writes can occupy the same executor needed by the field tasks
they synchronously await.

The revised prototype used an integer parallelism and a dedicated, writer-owned
Arrow `ThreadPool`:

```cpp
columnWriteParallelism_ =
    std::max<int32_t>(parquetWriterOptions.columnWriteParallelism, 1);
if (columnWriteParallelism_ > 1) {
  PARQUET_ASSIGN_OR_THROW(
      columnWriteExecutor_,
      ::arrow::internal::ThreadPool::Make(columnWriteParallelism_));
}
```

```cpp
if (columnWriteExecutor_) {
  builder.setUseThreads(true);
  builder.setExecutor(columnWriteExecutor_.get());
}
```

This removes the documented same-executor starvation scenario. The branch
exposed `writer.column-write-parallelism` and the session property
`writer_column_write_parallelism`; neither setting shipped in Velox.

## What the first benchmark got wrong

The original benchmark timed one complete in-memory file operation:

- writer and thread-pool construction;
- Velox-to-Arrow export;
- Arrow writer initialization;
- field writing;
- row-group and file close;
- output copies and teardown.

It also treated workers 1, 2, 4, and 8 as a core-scaling sweep. The VM actually
exposed four guest-visible cores and eight vCPUs with two SMT siblings per core,
so the 4-to-8 step added SMT siblings, not cores.

The resulting table was real for that end-to-end harness:

| Workers | Low-cardinality VARCHAR | Flat VARCHAR |
| ------: | ----------------------: | -----------: |
| 1       | 59.7 ms (1.00x)        | 877 ms (1.00x) |
| 2       | 56.8 ms (1.05x)        | 701 ms (1.25x) |
| 4       | 48.5 ms (1.23x)        | 607 ms (1.44x) |
| 8       | 39.1 ms (1.53x)        | 558 ms (1.57x) |

But its interpretation was not. Applying
[Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) to those values
produced an effective non-scaling fraction near 59% and a conditional ~1.7x
asymptote. We initially treated that model as an architectural diagnosis.

The follow-up phase tracing found the unstable portion outside the Arrow writer:
seven repeated `exportToArrow` calls took ~105-111 ms in fast samples and
~535-628 ms in slow samples, while compression and row-group close remained
stable. A model fitted to that mixed endpoint could not establish a Parquet
writer ceiling.

## The corrected study

The follow-up used a purpose-built executable with two separate endpoints:

1. **Velox integration lifecycle**, retaining export and sink costs.
2. **Direct Arrow writer lifecycle**, exporting and importing one immutable
   `RecordBatch` before timing.

The direct Arrow endpoint is the primary measurement for field-write scaling.
Its protocol was:

- Release build and the same binary for every treatment.
- AMD EPYC 9V45 virtual machine, four guest-visible cores / eight vCPUs with
  SMT topology, one socket, one NUMA node.
- Nested process cpusets `2`, `2,4`, and `2,4,6,1`, one SMT sibling from each
  guest-visible core. Workers could migrate within a cpuset; they were not
  individually pinned.
- 30 randomized paired blocks, one fresh process per treatment, five
  sacrificial writers per process, one recorded trial.
- Warm endpoint: seven row groups after the first, each containing 20 fields
  and 100K rows.
- Unadjusted percentile-bootstrap 95% confidence intervals for the median of
  the 30 block-wise latency ratios.
- Complete output buffers compared byte-for-byte between direct serial and
  threaded paths with one, two, and four workers.

The intervals are marginal, not simultaneous or family-wise intervals, and the
VM/cpuset choices limit generalization. The protocol nevertheless fixes the
specific confounders in the original study.

## Result 1: compression-heavy fields scale

The flat workload uses deterministic 128-byte VARCHAR values, disables Parquet
dictionary encoding, and enables ZSTD. Instrumentation measured about 264 MB of
input to ZSTD per row group.

| Configuration | Median warm latency | Speedup vs direct serial | Speedup vs threaded-1 |
| --- | ---: | ---: | ---: |
| Direct serial | 81.83 ms | 1.00x | 0.97x |
| Deferred serial, shared context | 82.56 ms | 1.00x | 0.97x |
| Deferred serial, per-field contexts | 78.68 ms | 1.03x | 1.00x |
| Threaded, 1 worker | 78.69 ms | 1.03x | 1.00x |
| Threaded, 2 workers | 45.12 ms | 1.81x | 1.74x |
| Threaded, 4 workers | 28.14 ms | 2.92x | 2.81x |

The one-worker controls are important. Deferred serial with per-field contexts
and threaded-one are effectively identical, showing that executor/future
overhead is small for this workload. Increasing the same threaded path from one
to four workers provides 2.81x [2.76, 2.84], equivalent to about 64.4% lower
latency.

Process CPU per row group increased from about 78.7 ms at one worker to 89.4 ms
at four, while wall time fell from 78.7 ms to 28.5 ms in instrumented diagnostic
runs. The extra CPU is the cost of reducing latency through concurrency.

## Result 2: Parquet dictionary encoding also scales

For 20 flat VARCHAR fields with cardinality 100, Parquet dictionary encoding
enabled, and ZSTD:

| Configuration | Median warm latency | Speedup vs direct serial |
| --- | ---: | ---: |
| Direct serial | 47.18 ms | 1.00x |
| Threaded, 1 worker | 47.56 ms | 0.99x |
| Threaded, 2 workers | 28.24 ms | 1.67x |
| Threaded, 4 workers | 18.25 ms | 2.58x |

Within the threaded path, four workers provide 2.64x [2.58, 2.66]. This result
tests Parquet dictionary encoding, not Arrow dictionary-array input: the export
step flattens the Velox dictionary before the direct Arrow benchmark begins.

## Result 3: lightweight fields regress

For 20 uncompressed BIGINT fields with Parquet dictionary encoding disabled:

| Configuration | Median warm latency | Paired latency change vs serial |
| --- | ---: | ---: |
| Direct serial | 16.78 ms | baseline |
| Threaded, 1 worker | 19.02 ms | 13.5% slower [12.5%, 14.7%] |
| Threaded, 2 workers | 17.90 ms | 6.3% slower [5.5%, 8.1%] |
| Threaded, 4 workers | 17.85 ms | 5.4% slower [4.2%, 7.0%] |

Here the threaded path's fixed overhead exceeds the benefit from parallel
execution. A production option therefore needs workload-aware defaults or must
remain opt-in; "more workers" is not an unconditional optimization.

## The one-field control

A single top-level field offers no field-level concurrency. Threaded-one was
1.160x [1.147, 1.165] faster than direct serial, demonstrating that the two paths
still have generic implementation differences. Relative to threaded-one, four
workers achieved 0.987x [0.923, 1.002]; the data neither detect a difference nor
establish equivalence. Two workers achieved 0.829x [0.729, 0.938]. Both
multiworker treatments were highly variable: 18.4% coefficient of variation at
two workers and 15.0% at four.

This is why worker scaling should be reported both against direct serial (the
user-visible treatment effect) and against threaded-one (the cleaner
worker-count effect).

## Memory remains a tradeoff

The Arrow writer always creates one serial `ArrowWriteContext`. Threaded mode
also creates one context per top-level field, whose buffers grow lazily.

A separate allocator experiment for 100K-row low-cardinality VARCHAR batches
measured about 200 KB of context-buffer allocation per field:

| Top-level fields | Serial context buffers | Threaded context buffers |
| ----------------: | ---------------------: | -----------------------: |
| 1                 | 200 KB                 | 200 KB                   |
| 4                 | 200 KB                 | 800 KB                   |
| 10                | 200 KB                 | 2.0 MB                   |
| 20                | 200 KB                 | 4.0 MB                   |
| 40                | 200 KB                 | 8.0 MB                   |

These are context buffers, not total writer memory. They exclude output
buffers, exported arrays, codec allocations, thread stacks, and pool objects,
and vary with batch shape, type, nullability, and nesting.

## What we can and cannot conclude

The corrected data supports these claims:

- On this VM, four-worker Arrow field writing is 2.92x [2.84, 2.95] faster than
  direct serial for the measured compression-heavy workload.
- Within the same threaded path, increasing from one to four workers gives
  2.81x [2.76, 2.84].
- Low-cardinality flat VARCHAR with Parquet dictionary encoding reaches 2.58x
  [2.52, 2.63] versus direct serial.
- Uncompressed BIGINT regresses by 5.4% [4.2%, 7.0%] at four workers.
- The previous ~1.7x ceiling and 58% serial-fraction inference are not supported.

The data does **not** support a hard ceiling, memory-bandwidth diagnosis, cache
diagnosis, or lock-contention claim. Hardware performance counters were
unavailable (`kernel.perf_event_paranoid=4`), and the VM exposes only four
guest-visible cores. A larger bare-metal core sweep, nested/skewed schemas, and
concurrent-file throughput under a fixed worker budget remain open work.

## Takeaways

- **Benchmark the component whose limit you are claiming.** End-to-end numbers
  are valuable, but they cannot diagnose the Parquet writer when an upstream
  export phase is unstable.
- **Include a one-worker treatment control.** Serial and threaded paths may
  differ in more than worker count.
- **Treat topology precisely.** Eight vCPUs on an SMT VM are not eight cores.
- **Use controlled workloads.** Disable dictionary encoding when testing flat
  compression, measure bytes reaching the codec, and include a lightweight
  negative control.
- **Publish corrected negative results.** The first experiment was useful
  because it exposed weaknesses in the measurement. The right response is to
  preserve that history and replace the unsupported conclusion with stronger
  evidence.
