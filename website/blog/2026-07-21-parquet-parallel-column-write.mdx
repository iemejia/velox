## TL;DR

The Arrow Parquet writer vendored by Velox already has a path that writes
top-level columns concurrently. We built an experimental Velox option around
that path using a dedicated, per-writer thread pool, then measured the complete
in-memory writer lifecycle on an eight-core machine.

At eight workers, the experiment reached **1.53x** on low-cardinality VARCHAR
data and **1.57x** on a much heavier flat VARCHAR workload. Both continued to
improve from four to eight workers, but with diminishing returns. Threaded mode
also retained one scratch context per top-level column in addition to the
writer's serial context.

For the heavier workload, the scaling curve is consistent with an idealized
[Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) model having an
effective non-scaling fraction of about 59%. If that fraction remained constant,
the model would approach roughly 1.7x. This is a workload-specific
extrapolation, not a measured architectural ceiling: the benchmark did not
separate serial work from scheduling overhead, contention, memory effects, or
task imbalance.

Given the measured gains, per-writer pool, per-column context memory, and added
support burden, the feature was not landed. The implementation remains on the
branch from [PR #18128](https://github.com/facebookincubator/velox/pull/18128)
in case future measurements change that decision.

## Background: where column concurrency exists

Velox writes Parquet through a vendored copy of Arrow's Parquet writer. For
each input batch, Velox exports the `RowVector` to an Arrow `RecordBatch` and
calls `FileWriter::writeRecordBatch`.

The Arrow writer first constructs one `ArrowColumnWriterV2` for each top-level
Arrow field. When threading is enabled, it then submits each writer's complete
`write()` operation through `::arrow::internal::ParallelFor`:

```cpp
if (arrowProperties_->useThreads()) {
  RETURN_NOT_OK(::arrow::internal::ParallelFor(
      static_cast<int>(writers.size()),
      [&](int i) {
        return writers[i]->write(&parallelColumnWriteContexts_[i]);
      },
      arrowProperties_->executor()));
}
```

The task is broader than compression and encoding. It also performs
definition- and repetition-level generation, physical conversion where needed,
statistics collection, page formation, and buffered serialization for the
field. A nested top-level field still corresponds to one task; its Parquet leaf
columns are processed within that task.

Some work remains outside `ParallelFor`. In particular, top-level column
writers and path builders are constructed before task submission, and buffered
column writers are closed in order when the row group is finalized. Source
inspection establishes that these phases are sequential, but it does not tell
us how much of the measured time they consume.

## The experiment

The first prototype added a Boolean option that enabled Arrow threading without
providing an executor. A null executor makes Arrow use its global process-wide
CPU pool. This gave Velox no control over the pool or its size and exposed the
documented starvation/deadlock scenario in which outer write operations occupy
the same executor needed by the column tasks they synchronously await.

The revised experiment made the parallelism an integer. When it was greater
than one, each Velox writer created and owned a dedicated Arrow `ThreadPool`:

```cpp
columnWriteParallelism_ =
    std::max<int32_t>(parquetWriterOptions.columnWriteParallelism, 1);
if (columnWriteParallelism_ > 1) {
  PARQUET_ASSIGN_OR_THROW(
      columnWriteExecutor_,
      ::arrow::internal::ThreadPool::Make(columnWriteParallelism_));
}
```

The pool was then passed explicitly to Arrow:

```cpp
if (columnWriteExecutor_) {
  builder.setUseThreads(true);
  builder.setExecutor(columnWriteExecutor_.get());
}
```

This design removes the documented same-executor starvation scenario because
the inner column tasks do not share the executor driving the outer writes. It
does not claim to eliminate every possible source of deadlock.

The experiment exposed two branch-only settings:

- connector config: `writer.column-write-parallelism` (integer, default 1)
- session property: `writer_column_write_parallelism`

These settings were proposed in #18128 but never shipped in Velox.

## Context-buffer memory

The Arrow writer always creates one serial `ArrowWriteContext`, which serial
mode reuses across fields. Threaded mode additionally creates one context per
top-level Arrow field so that field tasks do not share the definition-level and
physical-conversion buffers. Those per-field contexts are used by the tasks and
grow lazily as data is processed, while the serial context remains unused.

A separate allocator experiment measured the context-buffer allocations for
100K-row, low-cardinality VARCHAR batches. These figures are not total writer
memory: they exclude output buffering, exported Arrow arrays, encoder and
compressor allocations outside these contexts, thread stacks, and the thread
pool itself.

| Top-level columns | Serial | Threaded |
| ----------------: | -----: | -------: |
| 1                 | 200 KB | 200 KB   |
| 4                 | 200 KB | 800 KB   |
| 10                | 200 KB | 2.0 MB   |
| 20                | 200 KB | 4.0 MB   |
| 40                | 200 KB | 8.0 MB   |

At 20 columns, the measured context allocation remained 4.0 MB at two, four,
and eight workers. The count follows the number of top-level field tasks, not
the worker count. The approximately 200 KB per context is specific to this
100K-row VARCHAR case; context capacity varies with batch size, physical type,
nullability, and nesting.

## Benchmark methodology

The timing experiment used a release build on one eight-core development
machine. Each case wrote one batch containing 20 top-level VARCHAR columns and
100K rows with ZSTD enabled.

Input-vector construction was excluded from timing, but input-vector and
benchmark-pool destruction remained inside the timed region. The timed region
included:

- sink-pool and 200 MiB in-memory `MemorySink` construction;
- Velox writer and dedicated thread-pool construction;
- Velox-to-Arrow export and Arrow writer initialization;
- level generation, encoding, compression, and buffered column writes;
- row-group and file close, including in-memory output copying;
- writer, input-vector, and benchmark-pool destruction at the end of the
  operation.

The benchmark therefore measures a one-shot, in-memory writer lifecycle. It
does not measure filesystem or object-store I/O, and it does not isolate the
time spent in compression or in the Arrow `ParallelFor` region. The table below
contains the benchmark's reported point estimates; results on other hardware
or with long-lived writers may differ.

Two input shapes were compared:

- **Low-cardinality VARCHAR:** Velox dictionary-encoded input with cardinality
  100. The values are about 12 bytes each, and the Parquet writer can encode
  the repeated values compactly.
- **Flat 128-byte VARCHAR:** deterministic, high-cardinality hexadecimal
  strings. This case was intended to increase data-processing and compression
  work. It was about 14.7x slower in the serial benchmark, but compressor time
  and bytes passed to ZSTD were not measured separately, so we do not label it
  compression-bound.

## Results

| Workers | Low-cardinality VARCHAR | Flat 128-byte VARCHAR |
| ------: | ----------------------: | --------------------: |
| 1       | 59.7 ms (1.00x)        | 877 ms (1.00x)        |
| 2       | 56.8 ms (1.05x)        | 701 ms (1.25x)        |
| 4       | 48.5 ms (1.23x)        | 607 ms (1.44x)        |
| 8       | 39.1 ms (1.53x)        | 558 ms (1.57x)        |

The flat workload benefits earlier: it reaches 1.25x at two workers, while the
low-cardinality case reaches only 1.05x. At eight workers, however, the two are
close at 1.57x and 1.53x. Both still improve between four and eight workers, so
the accurate description is **diminishing returns through eight workers**, not
a plateau at four.

## Interpreting the curve with Amdahl's law

For speedup `S` on `n` workers with a constant non-scaling fraction `f`, the
idealized Amdahl model is:

```
S = 1 / (f + (1 - f) / n)
```

Solving for `f` at each flat-workload point gives:

| Workers | Measured speedup | Implied `f` |
| ------: | ---------------: | ----------: |
| 2       | 1.25x            | 60.0%       |
| 4       | 1.44x            | 59.3%       |
| 8       | 1.57x            | 58.5%       |

The three reported point estimates yield numerically similar implied fractions,
making the simple model a compact description of this workload's observed
scaling. No run-to-run variance or confidence intervals were recorded, so this
does not establish that the fraction is statistically stable. Using
`f ≈ 0.59`, the model's asymptotic speedup is:

```
1 / f ≈ 1.7x
```

That number needs careful interpretation. Here, `f` is an **effective
non-scaling fraction for this benchmark**, not a direct measurement of code
executing serially. It combines any work outside the parallel region with task
submission and synchronization overhead, allocator or memory-system
contention, imbalance among field tasks, and fixed benchmark-harness costs such
as `MemorySink` allocation and input teardown. The one-worker and threaded
cases also use different execution paths.

The benchmark did not profile those components separately. Source inspection
identifies sequential setup and ordered row-group finalization, while task
overhead, resource contention, memory-bandwidth limits, and field imbalance are
plausible additional contributors. Determining their shares requires phase
timing or profiling. The model therefore does not prove that every workload or
future implementation has a hard 1.7x ceiling.

The low-cardinality curve is less consistent with a constant-fraction Amdahl
model, which is another reason not to generalize the flat-workload estimate to
the entire writer.

## Why the feature did not land

The best measured results were 1.53x and 1.57x at eight workers. Against those
gains, enabling the existing Arrow parallel path in Velox would add a dedicated
pool to every enabled writer, retain context buffers per top-level field, and
create a configuration and execution mode that maintainers would need to
support. Writer and pool construction were part of this one-shot benchmark,
but the experiment did not isolate their individual cost.

Given that tradeoff, review feedback recommended not landing the option unless
additional data changed the picture, and PR #18128 was closed accordingly. The
executor-owning implementation remains on its fork branch if a different
executor strategy, workload, or writer architecture changes the result later.

The next useful step is not to assume a specific bottleneck, but to profile the
writer by phase: export and setup, field tasks, task scheduling and waiting,
row-group finalization, allocator behavior, and output copying. That would show
whether reducing sequential work, amortizing executor setup, or changing the
buffering architecture can move the curve.

## Takeaways

- **Measure the complete lifecycle.** Independent column tasks provide useful
  concurrency, but end-to-end gains also include setup, scheduling,
  synchronization, finalization, and memory behavior.
- **Use a heavier workload to challenge the result.** The 128-byte flat-string
  case was much slower serially, yet its eight-worker speedup remained close to
  the low-cardinality case. It did not, however, isolate compression as the
  cause.
- **Treat Amdahl's law as a model, not a profile.** A stable implied fraction
  can describe a scaling curve and suggest an asymptote, but it cannot identify
  the responsible code without additional measurements.
- **Record negative results with their scope.** The experiment establishes what
  happened for two workloads on one machine and explains why the option was not
  landed. It also leaves clear questions for the next investigation instead of
  presenting an extrapolation as an architectural fact.
